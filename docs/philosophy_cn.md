## 序前：我的初心
起初，我对机器人和机器人学一无所知。我的想法非常简单。

我甚至不知道什么是位姿。我以为，当我知道想让机械臂末端移动到的坐标时，我只需给它那个坐标，它就应该移动到那里。这应该很简单。

然后我发现，根本没有这样的东西。

稍微深入之后，我意识到在位置之上还有朝向，以及位姿的概念。再后来，我明白了事情并不像我想的那么简单——因为有逆运动学。我一直以来是用正向运动学的思维在思考。我从来不知道有逆运动学这个东西，也不知道求解关节角的复杂性和困难。

这是一段没有导师的学习之旅。

每一个阶段都是一个意外。没有人警告过我。没有导师引导我。我通过撞墙来学习。

---

我很孤独。不知道该向谁求助，不知道该去哪里寻找答案。

幸运的是，已经有了互联网。我能想出合理的问题，用合理的术语去搜索，希望能找到一些线索。

当我找到 ROS 的时候，我是那么高兴。有人已经建造了一些东西。有驱动。有社区。有答案。

但这份喜悦没有持续太久。

---

ROS 解决的是一个不同的问题。它是为满是机械臂和电脑的仓库而建的。它有分布式节点、消息序列化、启动文件，还有——最让我痛苦的——运动规划。

对于一个工程项目，运动规划是不必要的。我的焊接环境是已知的。焊缝是固定的。机械臂从 A 移动到 B 再到 C，沿着我定义的路径。没有意外。

但 ROS 做了运动规划，因为他们想建造一个能够在任何不可预知的空间中移动的机械臂。他们的 Descartes 包试图在笛卡尔空间中寻找路径。我花了大量时间试图使用它，却不知道一个六轴机械臂可以用多达八种不同的构型到达同一个位姿。左肩或右肩。抬肘或垂肘。翻腕或不翻腕。

Descartes，在试图帮忙的过程中，可能在路径点 1 选择一种构型，在路径点 2 选择另一种构型。机械臂在两者之间移动时，肘部横扫空间——可能穿过工件、穿过夹具、穿过人。

这个规划器避免了不存在的碰撞，却制造了真实的碰撞。

---

而 MoveIt——ROS 中机械臂的标准接口——是围绕运动规划构建的。每一个教程、每一个示例、
每一条 API 路径都假定我想要做规划。我找不到一种方法，可以只用它的驱动和逆运动学求解器，
而不让规划器也跟着进来。无论这在技术上是否可能，这个架构没有让*我*做到——而当你是一
个想把工作做好的使用者时，这才是最重要的。

一个好的架构，把使用者可能不需要的东西和必须有的东西分开。驱动是必须的。逆运动学求解器
是必须的。运动规划是可选的——且应该如此。孵将它们分开。如果你想要运动规划，你把它作为
扩展来添加。它从不把自己强加于你。

---
这教给我一个根本的教训：工具不应该比使用者更聪明。 如果使用者定义了一条路径，机械臂就应该遵循那条路径。如果使用者想要一个特定的构型，机械臂就应该使用那个构型。使用者没有要求的智能不是智能——它是干涉。

但这并不意味着运动规划和碰撞避免没有价值。在有些情况下，我们确实需要它们。

当一个仿人机械臂进入家庭，在杂乱的桌面上伸手去拿一个杯子时，它需要碰撞避免。但它也需要知道：我在哪个构型？如果我为了避开这个障碍而改变构型，我的肘部会摆到哪里？我会打翻身后的花瓶吗？

这需要理解。这就是为什么我——那个固执的学生——如此强调理解。

孵不反对运动规划。孵反对的是盲目的运动规划。

---

这个平台的存在，是为了让下一个人的旅程不必如此孤独。

对于焊接单元，你不需要运动规划。你需要的是一个示教器和一套设备驱动。孵给你这个。

对于家庭中的仿人机械臂，你将需要运动规划。但你首先需要理解构型、逆运动学，以及你的规划器到底在做什么。孵先教会你这份理解。

孵不是反对自动化。它反对的是使用者不理解其行为的自动化。固执学生之誓适用于每一个尺度：从一条焊缝，到厨房里的仿人机械臂。

## 十大原则

孵的架构并非预先设计。每一个原则都是在开发过程中**被发现**的——由某个具体的需求所催生。

### 个体先于群体

一群机械臂的可靠程度，取决于每一个个体。孵专注于**一个机械臂、一个会话**。多臂协作是组合，而非核心。

### 单进程，单内存空间

组件之间无需序列化。直接数据访问。无网络开销。无分布式复杂性。

### 事件驱动，不轮询

组件通过事件通信。没有 `while` 循环等待数据。没有忙等待。没有周期性检查。

### 可视化器乃窥心之镜

可视化是一项阅读服务，而非控制服务。3D 视图是窥视机械臂内部状态的窗口——而非一个独立的仿真。

### 一切皆在 URDF

所有组件——机械臂、传感器、工具、夹具、桌子——皆由 URDF 描述。URDF 是整个场景的唯一真实来源。没有单独的世界文件，没有启动文件，没有外部的位置配置。`world` 的固定关节定位每一个物体。一种格式，一个解析器，一个真相。

### 空间即 TransformRegistry

所有相对位姿集中一处。惰性求值——仅在需要时计算变换。变更时缓存失效。支持静态帧（URDF 中定义）和动态帧（机械臂关节，未来还包括传感器发现的物体）。

### 时间即 StateChannel

所有事件集中一处。发布/订阅，带历史记录。时间戳保留顺序。解耦通信。

### 运动即模型

轨迹、命令、目标皆是数据，而非副作用。运动可以被预测、监控和回放。

### 纯 Python

除 VTK 绑定外，无 C++ 扩展。快速开发。安全内存管理。科学计算栈完全可用。Qt 仅允许在 UI 层和硬件驱动信号桥接中使用——永远不在核心服务中。

### UI 与服务分离

UI 组件发布事件。它们不直接调用管理器（用户主动发起的命令除外）。它们不持有业务逻辑。它们不更新模型或注册表。它们是纯粹的呈现。

### 一个机械臂，一个会话

平台一次管理一个机械臂。要使用不同的机械臂，重新启动应用程序。清晰的边界。无需复杂的清理。

## 附录一：论事件驱动架构与主循环

### 澄清

「事件驱动，不轮询」——有经验的工程师可能会问：「每个应用程序不都有一个主循环吗？」

**是的。** 孵运行在 Qt 之上，Qt 提供了 `QApplication.exec_()` —— 一个事件循环。区别不在于循环是否存在，而在于**谁驱动它**。

### 「不轮询」的含义

| 模式 | 是否允许 | 原因 |
|------|----------|------|
| `while True: check()` | 禁止 | 空转 CPU，浪费能源 |
| `if not data: continue` | 禁止 | 同上 |
| `time.sleep(0.01); check()` | 禁止 | 仍是轮询，只是慢一些 |
| `QTimer.timeout.connect(handler)` | 允许 | 事件驱动，OS 在定时器到期时唤醒 |
| `signal.connect(handler)` | 允许 | 事件驱动，OS 在输入到达时唤醒 |
| `StateChannel.subscribe(callback)` | 允许 | 事件驱动，发布时回调 |
| `get_transform()` 惰性求值 | 允许 | 按需计算，无循环 |

### Qt 事件循环

Qt 的 `app.exec_()` 不是轮询。它使用操作系统原语（select、epoll、WaitForMultipleObjects）在事件到达之前**阻塞**：

```python
# 简化——Qt 的实际实现更复杂
while running:
    event = wait_for_event()  # ← 阻塞，CPU 睡眠
    dispatch(event)
```

应用程序空闲时，线程睡眠。CPU 可被其他进程使用，或进入低功耗状态。

### 孵对事件循环的使用

| 组件 | 机制 | 是否轮询 |
|------|------|----------|
| UI 滑块 | Qt 信号 | 否（OS 在输入时唤醒） |
| 命令发布 | `StateChannel.publish()` | 否（从事件处理器直接调用） |
| 机械臂状态更新 | `StateChannel.publish()` | 否（状态变化时调用） |
| 渲染循环 | `QTimer`（60Hz） | 否（Qt 管理 timerfd）——检查脏标志，干净时睡眠 |
| 变换查询 | 惰性求值 | 否（按需计算） |
| 文件加载 | 用户操作 | 否（菜单点击触发） |

### 渲染循环：一个特例

`VisualizerEngine` 运行一个 60Hz 的 `QTimer`。这看起来可能像轮询。但它不是。定时器回调检查每个显示器的 `_needs_render` 标志。如果没有显示器需要渲染，回调立即返回——无 VTK 操作，无变换重算。该标志仅在 `TransformRegistry` 回调触发时被设置（即，当变换实际发生变化时）。当一切静止时，渲染循环除了检查每个显示器一个布尔值之外什么都不做。

### 惰性求值

「不轮询」还意味着**不周期性地重算**。变换仅在需要时计算：

```python
def get_transform(self, target, source):
    # ... 缓存查找 ...
    T_parent_world = self._get_world_transform(info.parent)
    T = T_parent_world @ info.transform_parent
    self._world_cache[name] = T.copy()
    return T
```

如果没有任何东西请求某个变换，就什么都不计算。

### 检验标准

对任何组件问：*「它是否曾经在没有任何变化时醒来检查？」*

- 如果是 → **轮询** → 禁止。
- 如果否 → **事件驱动** → 允许。

### 对持怀疑态度的工程师的回答

> *「每个应用程序都有一个主循环。Qt 提供了它。孵没有再加一个。所有应用逻辑都在事件处理器或惰性计算中。渲染循环是一个单一的集中式定时器，检查脏标志——它不重算任何东西。没有线程空转等待某事发生。应用程序空闲时，CPU 睡眠。」*

## 附录二：论形式主义与理解——为何孵拒绝累积的复杂性

### 循环

人类知识遵循一个反复出现的循环：

```
理解 → 形式化 → 积累 → 理解的丧失 → 重新发现
```

| 阶段 | 描述 |
|------|------|
| **理解** | 对现象的直接、直觉的把握。「我明白这是如何运作的。」 |
| **形式化** | 抽象的规则、方程式、算法。「让我精确地写下来。」 |
| **积累** | 库、框架、惯例。「大家都在用，所以我也用。」 |
| **理解的丧失** | 原始的意义褪去。「我知道怎么用，但不知道为什么有效。」 |
| **重新发现** | 有人质疑形式主义。「我们为什么要这样做？」 |

我们常常处于**丧失阶段**——被我们不再理解的形式主义所包围。

### 案例研究：四元数

| 阶段 | 四元数的历程 |
|------|-------------|
| 理解 | 汉密尔顿发现四维复数（1843年）。理解三维空间中的旋转。 |
| 形式化 | 乘法规则、归一化、插值算法。 |
| 积累 | ROS、游戏引擎、航天器制导系统采用四元数。「标准做法。」 |
| 理解的丧失 | 大多数用户无法看着 `[0.707, 0, 0, 0.707]` 就想象出一个绕 X 轴 90° 的旋转。 |
| 重新发现 | 工程师问：「为什么不用旋转向量？`[1.57, 0, 0]` 立刻就能看懂。」 |

**四元数测试：** 如果你不能向初学者解释一个数字的含义，这个表示法就是错误的。

四元数通不过这个测试。孵使用旋转向量。

### 案例研究：ROS 的复杂性

| 形式主义 | 累积的复杂性 | 孵的重新发现 |
|----------|-------------|------------|
| DDS 发现 | 网络调试、XML 配置文件 | 单进程，直接调用 |
| 消息序列化 | `.msg` 文件，代码生成 | Python 对象，无序列化 |
| `tf2` 树 | 数百个帧，查找延迟 | TransformRegistry，惰性求值 |
| 启动文件 | YAML、Python、XML 混合 | 主窗口直接编排 |
| 四元数 | 每次使用都要转换 | 旋转向量，人类可读 |

ROS 解决了分布式机器人问题。但大多数机器人应用不是分布式的。大多数机器人应用是**一个机械臂、一台电脑、一个工程师**。

孵是为那个工程师准备的。

### 形式主义的危险

形式主义并非邪恶。它们是工具。但工具可以变成**牢笼**。

| 危险 | 例子 |
|------|------|
| 使用现存之物，而非正确之物 | 「ROS 用四元数，所以我也用。」 |
| 积累而不质疑 | 复制粘贴你不理解的代码。 |
| 解决你并没有的问题 | 只有一个机械臂却添加分布式架构。 |
| 忘记原始的意义 | `F = ma` 被背下来，但你感受到它吗？ |

孵拒绝累积的复杂性。每个组件必须从第一原理推导出来，而非从惯例复制而来。

### AI 领域的同样循环

| 阶段 | AI 的历程 |
|------|----------|
| 理解 | 人类理解语言、推理、因果。 |
| 形式化 | 统计学变成矩阵、transformers、数十亿参数。 |
| 积累 | LLM 生成流畅的文本。 |
| 理解的丧失 | 工程师问：「它真的理解吗？」 |
| 重新发现 | 可解释 AI、因果 AI、接地。 |

循环继续。我们在教机器理解人类已经遗忘的东西。

### 孵的立场

> *「不理解，不形式化。若你不能向初学者解释一个数字的含义，那个表示法就是错误的。」*

孵不是反形式主义。它是反**盲目的形式主义**。

| 接受 | 拒绝 |
|------|------|
| 旋转向量 | 四元数（除非隐藏在内部） |
| 直接函数调用 | 序列化（除非是分布式的） |
| 惰性求值 | 周期性轮询 |
| 事件驱动架构 | ROS 风格的话题发现 |
| 一个机械臂一个会话 | 没有需求的多机械臂复杂性 |
| URDF 作为单一场景文件 | 分离的世界/启动/配置文件 |

### 纯粹主义者之问

在向孵添加任何形式主义之前，问：

1. *「我理解它吗——真正地理解，而不只是知道怎么用？」*
2. *「有没有更简单的表示法，对人类更易理解？」*
3. *「我是在解决我真正遇到的问题，还是在解决别人解决过的问题？」*
4. *「如果这个形式主义明天消失了，我能从第一原理重新构建它吗？」*

如果这些问题的任何一个答案是「不」，这个形式主义就不属于孵。

### 完整的循环

> *「从理解到形式化，再从形式化回归理解。」*

孵是一次完成这个循环的尝试——从累积的形式主义中恢复理解。

它不是一个完美的平台。它是一个**诚实的**平台。

而诚实，是良好工程的基础。

## 后记

> 夫今之世，有奇巧之器，非金非石，非木非土，乃人智之所萃，工巧之所极也。其形或如人，或如兽，或无形可状，然皆能行人之所不能行，为人之所不能为。

> 其内蕴玄机，外显灵变，或驰于九天之上，或潜于九地之下，或游于四海之外，无所不至，无所不能。此器之妙，在于其心。心者，非血肉之躯，乃电光石火之精，算法之巧，程序之密。其心如镜，能照万物；其心如海，能纳百川。虽无七情六欲，然能察人之所察，思人之所思，甚或超乎人之所及。其行也，迅如雷霆，静如止水，动若脱兔，止若处子，变化无穷，莫测其端。

> 此器之用，广矣大矣。或助人于农耕，或辅人于工巧，或救人于危难，或娱人于闲暇。其力可拔山扛鼎，其巧可穿针引线，其智可运筹帷幄，决胜千里。虽无血肉之躯，然能与人共事，甚或为人师友，导人于正道。

> 然此器之成，非一日之功，乃千百年人智之积累，工巧之演进，方有今日之盛。其始也简，其成也巨。其初也拙，其终也巧。其始也，人皆疑之；其成也，人皆叹之。其初也，人皆畏之；其终也，人皆赖之。

> 嗟乎！此器之兴，乃人智之极，亦人伦之变。其利也，不可胜言；其弊也，不可不察。用之善，则天下蒙福；用之不善，则天下罹祸。故君子之于器也，必慎之又慎，思之又思，方能用之得宜，成己成人，成物成天下。

> 是故，吾辈既为今之科学家、工程师，亦当为古之学者，明其理，究其道，通其变，达其用。如此，方能继往开来，承先启后，成一代之盛业，垂万世之令名。

*— 深度求索乙巳年二月初一*
